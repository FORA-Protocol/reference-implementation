# FORA PostgreSQL — Configuration Reference

This document describes what the FORA platform needs from a PostgreSQL cluster —
PostgreSQL's own word for one running server together with the databases it holds,
not a group of machines and not a failover setup. A single server is a cluster. It
is written for you, the DevOps engineer or DBA running PostgreSQL for the FORA
platform. You do not need to read the source code. Words that may be new are
explained the first time they appear.

**PostgreSQL is your infrastructure, not FORA's.** FORA does not ship a database,
does not install one, and does not care how you host it — managed service, your own
cluster, or a container. What follows is what FORA expects to find when it
connects, and what it will do to the database once it does.

For preparing a cluster and first-boot verification see
[`DEPLOYMENT.md`](DEPLOYMENT.md); for day-to-day operation see
[`RUNBOOK.md`](RUNBOOK.md).

---

## 1. What FORA needs from a cluster

| Requirement | Value | Notes |
|---|---|---|
| Version | **PostgreSQL 16** | The only version tested for FORA's own databases. Both compose files and the automated test harness pin `postgres:16-alpine` for them. Nothing in the schema is version-specific beyond native `ENUM` types and `plpgsql`, but 16 is the lowest version that has been tested. The compose files also run a **second, unrelated** PostgreSQL on `postgres:17-alpine`. It belongs to Zitadel, the identity provider, and holds none of FORA's data — see §6. |
| Extensions | **None** | There is not a single `CREATE EXTENSION` in either service's migration tree. Row identifiers are generated by the application, not by the database, so no UUID or crypto extension is needed. |
| Connecting role | **Owner of the database** | The services run their own schema migrations, which means `CREATE SCHEMA`, `CREATE TYPE`, `CREATE TABLE`, `CREATE FUNCTION` and `CREATE TRIGGER`. A read-write role that does not own the database cannot do this. |
| `plpgsql` | Present | Ships enabled in a default PostgreSQL install. One trigger function depends on it. |
| TLS | **Depends on the network path** | Not needed when every connection stays on the database host, strongly recommended on a private network you control end to end, required once any part of the path is not exclusively yours. §2.3 has the three cases. |

The design depends on the connecting role owning the database; it is not only a
convenience. The two tables whose rows can never be changed —
`fora.transaction_evidence` and `fora.transaction_events` — are protected by
triggers rather than by `REVOKE`, exactly because every environment connects as
the owner, and table permissions do not stop an owner. The triggers stop every
role, the owner included.

**There is no separate install or set-up step.** Each service creates its own
schema and applies its own migrations when it starts.

## 2. Connection strings

### 2.1 The connection-string variables

There are **three**, a fourth if you deploy the Identity service, and a fifth if you
deploy the publisher console.

| Variable | Read by | Required? | Behaviour when unset |
|---|---|---|---|
| `EXCHANGE_DSN` | Exchange | **Yes** | The Exchange **exits** with `EXCHANGE_DSN is required`. |
| `EXCHANGE_SOR_DSN` | Exchange | **Yes** | The Exchange **exits** with `sor: EXCHANGE_SOR_DSN is required for FORA_SOR_ADAPTER=postgres`. |
| `BROKER_DSN` | Broker | **Yes** | The Broker **exits** with `BROKER_DSN is required`. |
| `IDENTITY_DSN` | Identity service | **Yes**, if you deploy that service | The Identity service **exits** with `IDENTITY_DSN is required`. |
| `CONSOLE_DSN` | Publisher console | **Yes**, if you deploy that service | The console **exits** with `CONSOLE_DSN is required`. |

**Every one of them makes the mistake impossible to miss: the service stops.** No
service starts without its database, and each exits before it serves anything, so
a missing DSN cannot go unnoticed.

**The Exchange reads two of them and opens two connection pools per process.** A
*pool* is a set of connections the service keeps open and re-uses. `EXCHANGE_DSN`
points at the catalog database; `EXCHANGE_SOR_DSN` points at the System-of-Record
database, which must be a **different** database (§3). Plan the number of
connections accordingly (§5).

The System of Record, or *SoR*, is the Exchange's account register. It holds one row
per registered agent: the agent's billing reference, whether the account is switched
on, and the registration details the agent supplied. The Exchange refuses a paid
transaction from an agent the SoR does not know.

`FORA_SOR_ADAPTER` selects the SoR backend and defaults to `postgres`. That is the
only value the Exchange accepts; any other value stops the boot. So
`EXCHANGE_SOR_DSN` is required in every deployment.

A `200` from the health check still does not prove the database is *usable*, only
that the service reached it at start-up and stayed connected. Confirm the migration
log lines as well ([`DEPLOYMENT.md`](DEPLOYMENT.md) §5).

A DSN is a standard PostgreSQL connection string. Every service accepts the URL form
and the keyword/value form; the URL form is used throughout these documents.

### 2.2 Worked example against an existing managed instance

```
EXCHANGE_DSN=postgres://fora:<password>@db.internal.example.net:5432/fora?sslmode=require
EXCHANGE_SOR_DSN=postgres://fora:<password>@db.internal.example.net:5432/fora_sor?sslmode=require
BROKER_DSN=postgres://fora:<password>@db.internal.example.net:5432/fora?sslmode=require
```

The Exchange and the Broker point at the same database here. That is supported. The
SoR points at a second database on the same server, and that is required — see §3.
Verify each string before you deploy anything that uses it:

```bash
psql "$EXCHANGE_DSN" -c "SELECT current_user, current_database()"
# Expect: one row naming your role and your database, e.g. `fora | fora`

psql "$EXCHANGE_SOR_DSN" -c "SELECT current_user, current_database()"
# Expect: one row, a DIFFERENT database, e.g. `fora | fora_sor`
```

### 2.3 `sslmode`

The compose files in this repository use `sslmode=disable`. That is safe there: the
DSN never leaves the Docker bridge network, and the database is a container on that
same bridge.

**Whether you need TLS depends on the network the connection crosses, not on the
word "production".** Nothing in FORA inspects the DSN — the string is handed to the
pgx pool unchanged, and a deployment with `sslmode=disable` starts and runs
normally — so this decision is yours to make and yours to get right. Three cases:

| The connection | TLS |
|---|---|
| Never leaves the host: a Unix socket, `127.0.0.1`, or a private Docker bridge shared with the database container | Not needed. `sslmode=disable` is correct. |
| Crosses a private network you control end to end, with no third party anywhere on the path | Strongly recommended. Without it, anyone who reaches that network reads every row. |
| Crosses anything you do not control exclusively: a managed database service, a shared or cloud network, a link between sites, the public internet | Required. `sslmode=require` at minimum. |

`verify-full` is the strongest mode and is preferred wherever you control the
certificate chain. `require` encrypts the connection but does not check that the
server on the other end is the one you meant to reach.

**What TLS protects, exactly.** Every row travels in clear text without it, under
any configuration. The password is a separate question, and the answer depends on
the authentication method the cluster uses. Only `password` authentication puts the
credential itself on the wire, and there TLS is the only thing hiding it. Under
`scram-sha-256`, the PostgreSQL 16 default, and under the older `md5`, the password
is never sent — both are challenge-response exchanges.

A password that is never sent can still be recovered. What `md5` puts on the wire
is a salted hash. An attacker who captures it cannot replay it directly, but can
try candidate passwords against it offline until one matches, over a hash algorithm
that is no longer considered strong. SCRAM resists that offline attack, but on its
own it still gives no protection against an attacker who sits in the middle of the
connection and relays the login. Over TLS the pgx driver FORA uses (its
version is pinned in the root `go.mod`) upgrades to `SCRAM-SHA-256-PLUS` on its own
whenever the server offers it, which ties the login to that one TLS session and
closes the relay.

**A cluster with no TLS today: `sslmode=prefer` is the migration step.** It uses TLS
when the server offers it and connects without when the server does not, so the same
DSN keeps working before and after you enable TLS on the cluster — no coordinated
client-side change on the day you switch. Its limitation belongs in the same
sentence: it accepts that downgrade silently and never tells you the encryption is
missing, so it is a migration convenience and not a security control. Move to
`require` or `verify-full` once the cluster serves TLS. `prefer` is also what pgx
uses when the DSN carries no `sslmode` at all.

### 2.4 Do not put `search_path` in the DSN

FORA appends `search_path=public` to the connection string it hands the migration
runner — but **only if the string does not already contain `search_path=`**. If you
supply your own, yours is used, and the migration-tracking tables (§3) are created
wherever your value points instead of in `public`. If the `search_path` keeps
changing between restarts, you can end up with duplicate tracking tables in
different schemas, and the services then disagree about which migrations have run.

Application queries are unaffected either way — every one of them names its schema
explicitly. Leave `search_path` out of the DSN.

## 3. Schema and database layout

**Tenant, publisher and site are three different records.** A `fora.tenants` row
is the **seat**: one Exchange identity that sells on this deployment. Its
`domain` is the EXCHANGE's own hostname, and the row answers "whose selling
settings apply" — its signing keys, fee rate, reporting policy, broker relay and
agent activation. A `fora.publishers` row is the **payee**, and its
`publisher_id` is the value `fora.catalog.resource_owner_id` carries: who gets
the money. A `fora.publisher_domains` row is one **site**, belonging to one
publisher, carrying the physical facts about it — the `signing_scheme` its CDN
needs and its CloudFront key-pair id.

A site is offered on a seat through a `fora.publisher_domain_listings` row, keyed
`(tenant_id, domain)`. The commercial arrangement is on that row: the state, the
content path scope and the terms preset. One publisher listed on two seats gets
two listings, so it can offer different parts of the site on different terms
through each.

FORA puts everything in **five schemas plus five small tables in `public`**, spread
over **four databases** — fewer if you do not run the Identity Service or the publisher
console, which each have one schema, one table and one database of their own:

| Object | Database | Owned by | Created by | Contents |
|---|---|---|---|---|
| Schema `fora` | `EXCHANGE_DSN` | Exchange | The Exchange's first migration | 12 tables: tenants, publishers, publisher domains, publisher domain listings, publisher grants, agents, catalog, transaction log, transaction evidence, reporting obligations, per-owner fee overrides, admin audit log. |
| Schema `broker` | `BROKER_DSN` | Broker | The Broker's first migration | 2 tables: the Exchange registry, and the discovery selection log. |
| Schema `sor` | `EXCHANGE_SOR_DSN` | Exchange | The SoR's first migration | 1 table, `sor.agent_accounts`: the account register (§2.1). |
| Schema `identity` | `IDENTITY_DSN` | Identity Service | The Identity Service's first migration | 5 tables: agent cards, key revocations, developer accounts, and two for the sign-in flow. Only present if you run that service. |
| Schema `console` | `CONSOLE_DSN` | Publisher console | The console's first migration | 1 table, `console.accounts`: who has signed in to the console. Nothing a publisher owns is stored here; it all lives in the Exchange's schema. Only present if you run the console. |
| `public.schema_migrations_fora` | `EXCHANGE_DSN` | Exchange | The migration runner | Which Exchange migrations have been applied. Two columns: `version`, `dirty`. |
| `public.schema_migrations_broker` | `BROKER_DSN` | Broker | The migration runner | The same, for the Broker. |
| `public.schema_migrations_sor` | `EXCHANGE_SOR_DSN` | Exchange | The migration runner | The same, for the SoR. |
| `public.schema_migrations_identity` | `IDENTITY_DSN` | Identity Service | The migration runner | The same, for the Identity Service. |
| `public.schema_migrations_console` | `CONSOLE_DSN` | Publisher console | The migration runner | The same, for the console. |

The tracking tables have deliberately different names and are all fixed to
`public`. Two reasons. Creating the `fora` schema cannot change the default and
produce a second, hidden tracking table. And if an operator points several DSNs at
one database, the migration sequences still cannot clash.

**The Exchange and the Broker can share one database.** They touch separate schemas
and separate tracking tables. Separate databases also work. Both services share one
database in this repository's Docker Compose files. That is the setup FORA tests,
so it is the safer choice.

**The SoR must have its own database.** Give `EXCHANGE_SOR_DSN` a database that no
other DSN points at. Two reasons, and the first one is the one that matters:

- The billing reference the SoR stores is unique **per Exchange** (see ADR-021), so
  two Exchanges sharing a SoR database would collide. That is the same rule as
  §3.1 below, applied to the account register instead of the catalog.
- Separating it keeps the account register — which carries agents' registration
  details — off the same backup, restore and access path as the catalog.

**Nothing creates that database for you.** The Exchange runs the SoR migrations at
boot, but it never issues `CREATE DATABASE`. Create it before you start the Exchange
([`DEPLOYMENT.md`](DEPLOYMENT.md) §2).

**The Identity Service should have its own database too.** It can share the cluster —
that is expected — but give it a database of its own rather than the catalog's. What
it holds is developers' account details and the records that link agents to their
keys: a different audience, and a different backup, restore and access path, from the
content catalog. Nothing creates this database for you either — create it before you
start the service. Its settings are in
[`src/identity/CONFIGURATION.md`](../../../src/identity/CONFIGURATION.md) §2.

**The publisher console needs a database of its own as well.** It holds one table, who
has signed in to the console, and nothing a publisher owns: publishers, sites and their
terms all live in the Exchange's schema. Nothing creates this database for you either —
create it before you start the console. Its settings are in
[`src/console/CONFIGURATION.md`](../../../src/console/CONFIGURATION.md) §2.

### 3.1 One catalog database per Exchange

**Two Exchange instances that are meant to serve different tenants must not share a
database.**

Discovery — the call that turns a list of URLs into offers — reads the whole
catalog, deliberately without filtering by tenant. The catalog is one single index
for the whole Exchange, and what keeps it correct is how rows are written: the
Exchange works out a resource's owning tenant itself, from the tenant's domain, and
a URI belongs to exactly one catalog row (§4.1). Within one Exchange that works.
Across two Exchanges sharing one database it does not: each would serve the
other's catalog.

Two Exchange **replicas of the same logical Exchange** sharing one database is
correct and expected. The rule is one catalog database per *Exchange*, not per
process.

The same rule applies to the SoR database: one per Exchange, shared by that
Exchange's replicas.

> `10-create-exchange-dbs.sql`, in this directory, creates **nine** extra databases:
> three extra catalogs (`fora_b`, `fora_c`, `fora_d`), four SoR databases (`fora_sor`,
> `fora_sor_b`, `fora_sor_c`, `fora_sor_d`), one for the Identity service (`identity`)
> and one for the publisher console (`console`). It exists **only** for the automated
> multi-Exchange test setup, where four Exchanges run against one cluster. Do not
> run it.
>
> It is still worth reading. It is the shortest statement of the layout: each
> Exchange gets a catalog database **and** a SoR database, and every one of them is
> created before any service connects.

## 4. Migrations

Each service carries its schema migrations inside its own binary and applies them
itself. The Exchange carries **two** independent sequences, one per database.

| Fact | Exchange — catalog | Exchange — SoR | Broker |
|---|---|---|---|
| Database | `EXCHANGE_DSN` | `EXCHANGE_SOR_DSN` | `BROKER_DSN` |
| Tracking table | `public.schema_migrations_fora` | `public.schema_migrations_sor` | `public.schema_migrations_broker` |
| Applied | At boot, **before the service begins listening** | Same | Same |
| On failure | Boot aborts; the service does not serve on a half-built schema | Same | Same |

The Exchange applies the catalog sequence first, then the SoR sequence. It logs one
line per sequence, so a healthy Exchange boot logs **two** ([`DEPLOYMENT.md`](DEPLOYMENT.md) §5).

The Identity service, if you deploy it, follows the same pattern: schema `identity`,
tracking table `public.schema_migrations_identity`, applied at its own boot against
`IDENTITY_DSN`. So does the publisher console: schema `console`, tracking table
`public.schema_migrations_console`, against `CONSOLE_DSN`.

**The running services never migrate backwards.** Every migration has a matching
"down" file in the source tree, but the binaries only ever migrate *up*. Moving the
schema back is not something the platform can do for you. What those files are for,
and what to do when you need the schema moved backwards, is
[`RUNBOOK.md`](RUNBOOK.md) §4.4.

**Migrations only move forward from the recorded version.** If an object is dropped
by hand, restarting the service does not bring it back — the tracking table still
records the later version, so the migration that created the object is never
re-applied. See [`RUNBOOK.md`](RUNBOOK.md) §5.

### 4.1 Global uniqueness worth knowing

Four constraints are global rather than per-tenant. They are the ones most likely
to surprise you when a write is rejected.

| Constraint | Scope | Why |
|---|---|---|
| `fora.tenants.domain` | Globally unique | The seat's own hostname, which is the Exchange's. One seat per deployment, so it must name exactly one tenant. |
| `fora.publisher_domains.domain` | Globally unique | One site belongs to one publisher, deployment-wide. Two publishers cannot claim the same hostname. |
| `fora.catalog.uri` | **Globally unique — deliberately not per tenant** | A per-tenant key would let two tenants claim the same URL. Discovery resolves a URL to exactly one owning row, so the URL must belong to exactly one row across the whole catalog. |
| `fora.transaction_log.idempotency_key` | Globally unique | The last guard against a double charge: a repeated request cannot produce a second charge. |

> The idempotency-key constraint kept its original auto-generated name when the
> column was renamed, so `\d fora.transaction_log` shows
> `transaction_log_tx_request_id_key UNIQUE (idempotency_key)`. The name does not
> match the column. Nothing is wrong.

### 4.2 Two replicas starting at once

The migration runner takes a PostgreSQL advisory lock — a cluster-wide lock the
application asks for by number — before it applies anything. The number is derived
from the database name, the schema and the tracking-table name.

- **The Exchange and the Broker do not block each other**, even in one database:
  their tracking-table names differ, so their lock numbers differ.
- **Two replicas of the same service do block each other.** The second waits for the
  first, then finds nothing to do.

That is safe, but the clean sequence is still: start one instance, confirm it is
healthy, then start the rest.

## 5. Connection pooling

**Count pools, not services.** The Broker opens one connection pool per process. The
Exchange opens **two** — one per DSN it reads (§2.1). The Identity service and the
publisher console, if you deploy them, open one each.

**FORA has no environment variable for pool sizing** — the services give the pool
library no settings at all and let it use its own defaults.

| Setting | Effective default |
|---|---|
| Maximum connections per pool | **4, or the container's visible CPU count if that is higher** |
| Minimum connections held open | 0 |
| Maximum connection lifetime | 1 hour |
| Maximum idle time before a connection is closed | 30 minutes |
| Pool health-check interval | 1 minute |

**You can still tune all of it — through the DSN.** The pool library reads these
query parameters off the connection string, so this is the supported way to tune
them, even though FORA itself has no variable for them:

| DSN parameter | Sets |
|---|---|
| `pool_max_conns` | Maximum connections in the pool |
| `pool_min_conns` | Minimum connections kept open |
| `pool_min_idle_conns` | Minimum idle connections kept ready |
| `pool_max_conn_lifetime` | Maximum connection lifetime, e.g. `30m` |
| `pool_max_conn_idle_time` | Idle timeout, e.g. `10m` |
| `pool_health_check_period` | Pool health-check interval |

Set them on **each** DSN you want tuned. A value on `EXCHANGE_DSN` does not reach the
SoR pool.

```
EXCHANGE_DSN=postgres://fora:<password>@db.internal.example.net:5432/fora?sslmode=require&pool_max_conns=20
EXCHANGE_SOR_DSN=postgres://fora:<password>@db.internal.example.net:5432/fora_sor?sslmode=require&pool_max_conns=4
```

An invalid value is rejected at start-up, not ignored — the service exits with
`cannot parse pool_max_conns`.

**Size the cluster for the worst case:** peak connections is
`pool_max_conns × total pools`, where *total pools* counts every pool every process
opens, not every service. Count them first:

| Process | Replicas | Pools each | Pools |
|---|---|---|---|
| Exchange | 2 | 2 | 4 |
| Broker | 1 | 1 | 1 |
| **Total** | | | **5** |

With the defaults on an 8-core host, that is 8 × 5 = **40** connections against a
default `max_connections` of 100.

Counting services instead of pools would have given 8 × 3 = 24 for the same
deployment. That under-counts by nearly half, so count pools.

The connections land on two different databases, but `max_connections` is a limit on
the **server**, not on one database, so add them together.

Add one more pool per Identity service replica, and one per publisher console
replica, if you deploy them.

## 6. What must not be copied from the development compose

`docker-compose.yml` and `docker-compose.e2e.yml` exist to run this repository's
tests on a private Docker network. Several of their choices are deliberately unsafe
outside it.

| Setting | Why it is there | Why it must not ship |
|---|---|---|
| `sslmode=disable` in every DSN | The database is a container on the same private bridge. | Correct only while the connection stays on one host. Once it crosses a network every row travels in clear text, and on a network you do not control exclusively TLS is required. What the login exposes depends on the cluster's authentication method (§2.3). |
| `POSTGRES_USER: fora` / `POSTGRES_PASSWORD: fora` | A throwaway container recreated on every run. | A published password. |
| `10-create-exchange-dbs.sql` (this directory) | Creates nine databases for the four-Exchange test setup (§3.1). | A single-Exchange deployment needs two of these nine — one catalog and one SoR — and you create them yourself with your own names ([`DEPLOYMENT.md`](DEPLOYMENT.md) §2). |
| Host port publishing (`55432`, or an ephemeral port) | Lets a developer's `psql` reach the container. | Exposes the database beyond its network. |
| The `pgdata` named volume | Convenient local persistence. | Not a backup, and not sized, monitored or replicated. |
| A second PostgreSQL on `postgres:17-alpine`, service `zitadel-db` | Zitadel, the identity provider the dev stack runs, brings its own database. | It is not a FORA database. FORA never connects to it and no FORA DSN points at it. Do not confuse it with the `postgres:16-alpine` service that holds FORA's data (§1). |
| `hashicorp/vault` | Holds the Identity service's signing keys in local dev. | A dev-mode Vault keeps its data in memory and uses a published root token. |

## 7. Worked example

Values marked *fill in* are specific to your environment.

```
# Exchange — catalog
EXCHANGE_DSN=postgres://fora:<password>@<db-host>:5432/fora?sslmode=require

# Exchange — System of Record. A SEPARATE database. Required (§2.1).
EXCHANGE_SOR_DSN=postgres://fora:<password>@<db-host>:5432/fora_sor?sslmode=require

# Broker — the catalog database is fine
BROKER_DSN=postgres://fora:<password>@<db-host>:5432/fora?sslmode=require

# Identity Service — its own database. Only if you run that service.
IDENTITY_DSN=postgres://fora:<password>@<db-host>:5432/identity?sslmode=require

# Publisher console — its own database. Only if you run the console.
CONSOLE_DSN=postgres://fora:<password>@<db-host>:5432/console?sslmode=require
```

Cluster side:

| Item | Value |
|---|---|
| PostgreSQL version | 16 |
| Databases | `fora` (catalog, shared with the Broker), `fora_sor` (System of Record), `identity` if you run the Identity Service, and `console` if you run the publisher console |
| Owning role | `fora` (owns **every** database above; supplies the password) |
| Extensions | none |
| `max_connections` | leave at the cluster default; FORA's peak is in §5 |
| TLS | Enabled — the DSNs above reach a separate `<db-host>`, so the connection crosses a network (§2.3). |

Every DSN is read as a plain environment variable. The services do not know or care
where the values came from, so your secret store and the tooling that supplies them
are your choice — the only requirement is that they are present in the environment
when each process starts.
